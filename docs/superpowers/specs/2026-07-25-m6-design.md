# M6 Design — Delivery, Communication, AI QA, Closeout, Feedback

Date: 2026-07-25  
Status: Approved  
Milestone: M6  
Spec reference: `SPEC - Complete MVP A.md §4`

---

## Purpose

Prove ≤10-hour fixed-scope work can be delivered, reviewed with AI QA help, and closed out reliably, with structured (not open) communication. Completes Gate 6.

---

## Decisions captured

- **AI QA input:** Consultant provides a text summary/notes at submission time; AI QA runs against that summary + scope deliverable + acceptance criteria. No file content parsing.
- **AI QA exposure:** Auto-expose to client immediately — no admin gate on QA notes for MVP A.
- **High-risk trigger:** Single trigger — if AI QA returns `riskFlag: true`, creates an `AdminTask` and blocks client acceptance until admin resolves it.
- **Feedback:** Collected via in-page form on the engagement page when status is `CLOSED` (client and consultant each submit separately). No email link for MVP A.
- **Communication types:** `CommunicationType` enum enforced in schema + service + UI.
- **Resubmission:** Explicit resubmit button after a revision request, creates a new `Deliverable` row linked to the `RevisionRequest`, marks the request `ADDRESSED`.
- **"Revision Due Soon" notification:** Deferred — requires cron infrastructure not yet built. M7.

## Section 1: Schema Changes

One migration covers all of the following.

### `CommunicationType` enum (new)

```prisma
enum CommunicationType {
  CLARIFICATION
  DOCUMENT_REQUEST
  REVISION_RESPONSE
  ISSUE_FLAG
}
```

`EngagementCommunication.messageType` changes from `String` to `CommunicationType`.

### `Deliverable` additions

```prisma
consultantNotes  String?
aiQaNotes        String?
aiQaRiskFlag     Boolean   @default(false)
aiQaRunAt        DateTime?
revisionRequestId String?  // links resubmission to the revision that triggered it
```

`revisionRequestId` is a nullable FK to `RevisionRequest`.

### `RevisionRequest` additions

```prisma
inScopeConfirmation Boolean  @default(true)
dueDate             DateTime?
```

### `Feedback` model (new)

```prisma
model Feedback {
  id           String   @id @default(cuid())
  engagementId String
  submittedBy  String   // userId
  role         Role
  satisfaction Int      // 1–5
  repeatIntent Boolean
  comments     String?
  createdAt    DateTime @default(now())

  engagement Engagement @relation(fields: [engagementId], references: [id])

  @@unique([engagementId, submittedBy])
}
```

The `Engagement` model must also add `feedbacks Feedback[]` to its relation list.

### `AdminTask` flesh-out (currently a stub)

```prisma
model AdminTask {
  id           String   @id @default(cuid())
  engagementId String?
  deliverableId String?
  reason       String
  resolved     Boolean  @default(false)
  createdAt    DateTime @default(now())
}
```

## Section 2: Service Layer

### `modules/deliverables/service.ts`

**`submitDeliverable(engagementId, fileUrl, consultantNotes, actorId)`**
- Replaces the current thin `createDeliverable`.
- Creates `Deliverable` with status `SUBMITTED`, populates `fileUrl` and `consultantNotes`, sets `submittedAt`.
- Transitions engagement `IN_PROGRESS → DELIVERABLE_SUBMITTED` within the same transaction.
- Logs event.
- After transaction: fires `runAiQa(deliverableId, actorId)` (fire-and-forget) and sends "Deliverable submitted" admin email.

**`resubmitDeliverable(engagementId, revisionRequestId, fileUrl, consultantNotes, actorId)`**
- Creates a new `Deliverable` row with `revisionRequestId` populated.
- Within one transaction: marks `RevisionRequest` as `ADDRESSED`, transitions engagement `REVISION_REQUESTED → IN_PROGRESS → DELIVERABLE_SUBMITTED`.
- After transaction: fires `runAiQa` on the new deliverable.

**`runAiQa(deliverableId, actorId)`**
- Fetches deliverable + engagement + scope.
- Calls Claude with: scope deliverable description + acceptance criteria + consultant notes as context.
- Prompt instructs Claude to return JSON `{ notes: string, riskFlag: boolean }`.
- Writes `aiQaNotes`, `aiQaRiskFlag`, `aiQaRunAt` on the `Deliverable`.
- Transitions engagement `DELIVERABLE_SUBMITTED → UNDER_REVIEW`.
- Writes `AIOutputLog` row (touchpoint `deliverable_qa`, exposed `true`, reviewed `false`).
- If `riskFlag === true`: creates `AdminTask` row with `engagementId`, `deliverableId`, reason `"AI QA risk flag"`.
- After DB writes: sends "AI QA complete" email to client.

**`createFeedback(engagementId, submittedBy, role, satisfaction, repeatIntent, comments)`**
- Upsert on `[engagementId, submittedBy]` unique constraint.

### `modules/engagements/service.ts`

**`acceptEngagement` — guard added:**
- Before transitioning to `ACCEPTED`: fetch latest deliverable for the engagement. If `aiQaRiskFlag === true`, check for an unresolved `AdminTask` on that deliverable. If one exists, throw `"Acceptance blocked: AI QA risk flag requires admin review"`.
- On success: transition `UNDER_REVIEW → ACCEPTED`, log event, call `closeProject`.

**`closeEngagement` — email added:**
- After `ACCEPTED → CLOSED`: sends "Engagement closed — please leave feedback" email to both client and consultant.

**`resolveAdminTask(adminTaskId, actorId)`** (new, in `modules/admin/service.ts` or inline):
- Sets `AdminTask.resolved = true`, logs event.

### `modules/communications/service.ts`

**`sendMessage`:**
- `messageType` parameter type changes from `string` to `CommunicationType`.
- TypeScript enforces valid values at compile time; no runtime validation needed beyond type checking.

## Section 3: UI Surfaces

### Consultant engagement page (`/engagements/[id]`)

**Submission form (when `IN_PROGRESS`):**
- File input (existing) + `consultantNotes` textarea (required, new).
- Submit calls `submitDeliverableAction`.

**Post-submission (when `DELIVERABLE_SUBMITTED`):**
- Shows "AI QA running..." until `aiQaRunAt` is set.
- Once QA complete: shows `aiQaNotes`.

**Revision state (when `REVISION_REQUESTED`):**
- Shows open `RevisionRequest`: reason, due date, in-scope flag.
- "Resubmit" form: file + notes → calls `resubmitDeliverableAction`.

**Feedback (when `CLOSED`):**
- Satisfaction (1–5), repeat intent (yes/no), optional comments.
- Calls `createFeedbackAction`.

**Communications panel (all states):**
- Type dropdown: `Clarification | Document Request | Revision Response | Issue Flag`.
- Body textarea + send button.
- Message history below (type badge + sender role + timestamp + body).

### Client engagement page (`/projects/[id]/engagement/[engagementId]`)

**Deliverable section:**
- File link + consultant notes + AI QA notes (auto-exposed).
- Accept button: disabled with message `"Under admin review — acceptance temporarily blocked"` if `aiQaRiskFlag === true`.
- Request Revision: reason textarea (replaces hardcoded string). No client-side due date.

**Feedback (when `CLOSED`):**
- Same form as consultant side.

**Communications panel:**
- Same type dropdown + message history.

### Admin engagement page (`/admin/engagements/[id]`)

**Deliverable section:**
- File link, consultant notes, AI QA notes, risk flag badge (amber if flagged).
- If `aiQaRiskFlag === true`: shows open `AdminTask` + "Mark Resolved" button → calls `resolveAdminTaskAction`.

**Revision request section:**
- In-scope confirmation checkbox + due date field (admin sets these via `updateRevisionRequestAction`).

**Closeout:**
- "Close Engagement" button visible when status is `ACCEPTED`.

**Communications:**
- Full history, all types, all parties.

## Section 5: Notifications

All emails fire-and-forget after transactions, via `lib/email.ts`.

| Event | Recipient | Trigger |
|---|---|---|
| Deliverable submitted | Admin | `submitDeliverable` |
| AI QA complete | Client | end of `runAiQa` |
| Revision requested | Consultant | `requestRevision` |
| Engagement closed + feedback prompt | Client + Consultant | `closeEngagement` |

**Deferred:** "Revision Due Soon" — requires cron, deferred to M7.

## Verification (Gate 6 criteria)

- Closeout cannot complete without AI QA having run (`aiQaRunAt` must be set; enforced in `acceptEngagement` guard)
- A revision request records `inScopeConfirmation` and `dueDate` (admin sets; both fields present on the record)
- AI QA risk flag creates an `AdminTask` and blocks silent client closeout
- Client sees AI QA notes immediately (no gate); raw `AIOutputLog` is never exposed to client
- Communication is constrained to `CommunicationType` enum values
- Feedback can be submitted by both client and consultant after `CLOSED`; duplicate submission upserts
